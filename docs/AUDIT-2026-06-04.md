# Coco Language Design Audit — 2026-06-04

**Status:** Phase 0-1 validation FAILED — critical spec inconsistencies block approval

**Auditors:** Codewhale, Codex, Claude Code (cross-reference audit)

**Summary:** The language design is fundamentally sound with clear identity and good safety principles, but the formal grammar, documentation, examples, and tooling have drifted into incompatibility. Examples use syntax the grammar doesn't support. This must be resolved before Phase 0-1 can be considered complete.

---

## Executive Summary

### What Works Well ✅
- **Clear language identity** — charter defines target users, workloads, and philosophy
- **Strong safety story** — 10 concrete guarantees, automatic memory management
- **Good error handling split** — Result for expected, exceptions for bugs
- **Strict race prevention** — compile-time rejection of unsafe parallelism
- **Gradual typing with escape hatch** — mixed type + narrowing is well-designed
- **15 ratified ADRs** — all have clear context, decision, and consequences
- **20 working examples** — demonstrate language feel and validate design

### Critical Issues ❌
1. **Grammar-example mismatch** — examples use `function`, `f`, async closures, destructuring, `chan<T>()`, `super()`, `as` casts that the EBNF grammar doesn't define
2. **Quote ambiguity** — `'a'` matches both `char_literal` and `string_literal` productions
3. **Inconsistent atomic syntax** — docs use both `atomic(0)` and `new Atomic<int>(0)`
4. **Missing module resolution spec** — no ADR for how imports resolve
5. **No stdlib design** — examples reference `std/http`, `std/db`, `DateTime`, `JSON`, etc. with zero specification
6. **No FFI specification** — `ffi.load()` is shown but not defined
7. **No build system design** — no package manifest, dependency, or compilation spec
8. **Unresolved type system details** — `__get/__set` type checker interaction, trait method conflicts, match exhaustiveness, object vs map literals

### Verdict

**Phase 0-1 cannot be approved until:**
- Grammar supports all syntax used in examples
- Quote ambiguity is resolved
- Atomic syntax is standardized
- Module resolution ADR is written
- Stdlib outline ADR is written

## Detailed Findings

### Category: Spec Bugs (Must Fix Before Phase 2)

#### 1. CRITICAL: `function` and `f` keywords missing from EBNF

**Issue:** Documentation, CLAUDE.md, README, and all examples consistently show three equivalent function keywords: `function`, `fn`, `f`. The EBNF grammar only supports `fn`.

**Evidence:**
- `docs/grammar.ebnf:31` — `fn_decl = [ "async" ] , "fn" , identifier , ...` (no `function` or `f`)
- `docs/grammar.ebnf:59` — `method_decl = [ "async" ] , [ "fn" ] , identifier , ...` (no `function` or `f`)
- `docs/grammar.ebnf:216` — anonymous functions only support `fn(...)`, not `function(...)` or `f(...)`
- `examples/03-functions.co:8` — uses `function add(...)`
- `examples/03-functions.co:18` — uses `f multiply(...)`
- `examples/03-functions.co:25` — uses `const divide = function(...)`
- `docs/language-reference.md:66-78` — explicitly documents all three keywords
- `README.md:121-133` — shows examples with all three keywords

**Impact:** Parser cannot parse 7 of the 20 example files. ADR-001 ratifies the shorthand forms but the grammar contradicts it.

**Fix:** Add `function` and `f` alternatives to:
- `fn_decl` (named functions)
- `method_decl` (class methods)
- `method_signature` (interface/trait methods)
- `primary_expr` (anonymous functions)

#### 2. CRITICAL: Single-quote ambiguity (char vs string)

**Issue:** The grammar defines:
```ebnf
string_literal = '"' , { string_char } , '"'
               | "'" , { char_content } , "'" ;
char_literal = "'" , char_content , "'" ;
```

`'a'` matches both productions — `char_literal` (exactly one `char_content`) and `string_literal` (zero-or-more `char_content`). This is ambiguous.

**Evidence:**
- `docs/grammar.ebnf:249-250` — string allows single quotes
- `docs/grammar.ebnf:258` — char uses single quotes
- No language doc clarifies precedence or disambiguation

**Impact:** Parser cannot distinguish `'a'` as char vs string. Lexer ambiguity.

**Fix (Recommended):** Drop single-quoted strings entirely. Use:
- Single quotes `'a'` for `char` only
- Double quotes `"hello"` for `string` only
- Backticks `` `template` `` for template strings

This matches Rust, TypeScript (with strict quotes), and eliminates ambiguity.

**Alternative Fix:** Keep both but require string literals to be 0 or 2+ characters in single quotes (not 1), pushing single-char literals to `char`. This is complex and error-prone.

#### 3. HIGH: Inconsistent `atomic` syntax

**Issue:** Two different syntaxes appear in docs:

**Function-style (concurrency.md, README.md):**
```coco
let counter = atomic(0);
```

**Constructor-style (language-reference.md troubleshooting):**
```coco
const counter = new Atomic<int>(0);
```

**Evidence:**
- `README.md:237` — `let counter = atomic(0);`
- `docs/concurrency.md` — uses `atomic(...)` function form
- `docs/language-reference.md:730` — `const counter = new Atomic<int>(0);`
- `examples/09-parallel.co:34` — `let total = atomic(0);`

**Impact:** Unclear what the canonical syntax is. Does `atomic` return a type? Is it generic? Is it a builtin function or a class constructor?

**Fix:** Choose one and make all docs consistent. Recommendation:
- **Constructor form** `new Atomic<int>(0)` — explicit, works with generics, consistent with `new` keyword usage
- Update README, concurrency.md, and examples to match

#### 4. HIGH: Examples use syntax not in grammar

**Missing grammar support:**

| Syntax | Used In | Grammar Status |
|--------|---------|---------------|
| `async function() {}` | examples/03-functions.co:68 | Not in `primary_expr` |
| `async fn() {}` | multiple files | Not in `primary_expr` |
| `async (x) => {}` | Not yet used, but implied | Not in `arrow_fn` |
| `const [a, b, c] = ...` | examples/09-parallel.co:19 | No destructuring |
| `chan<T>(size)` | examples/10-channels.co:28 | Not in grammar |
| `super.method()` | Implied by inheritance | `super` not in grammar |
| `value as Type` | Implied by docs | `as` cast not in grammar |
| `export type X = ...` | Implied by modules | `export type` not in grammar |
| `0..count` | examples/10-channels.co:21 | Range syntax not in grammar |
| `private async fn` | May be used | Modifier before `async` unclear |

**Impact:** Parser will reject valid examples. Phase 0-1 exit criteria states "20 examples parse against EBNF."

**Fix:** Add grammar rules for all of the above.

### Category: Major Design Gaps (Must Address Before Implementation)

#### 5. HIGH: No module resolution specification

**Issue:** Grammar has `import` and `export`. Examples use `"std/http"` and `"./database"`. But there's no specification for:
- How `"std/http"` maps to filesystem
- Whether there's a `coco_modules` or `vendor` directory
- How relative imports resolve (to file? directory? package?)
- Project root detection (coco.toml? git root?)
- Circular import handling
- Tree-shaking with `import * as X`

**Evidence:**
- `examples/11-http-server.co:1` — `import { Server } from "std/http";`
- `examples/20-queue-worker.co:3` — `import { Context } from "std/process";`
- No ADR or spec document addresses module resolution

**Impact:** Parser can parse imports but can't resolve them. Compiler can't find module sources.

**Fix:** Write **ADR-016: Module Resolution** covering:
- Standard library path (`std/` prefix)
- Relative imports (`./`, `../`)
- Package imports (future: `pkg/name`)
- File extension rules (`.co` required? optional?)
- Directory modules (index.co? module.co?)
- Circular import policy (allowed? detected? error?)

---

#### 6. HIGH: No standard library design

**Issue:** Examples reference extensive stdlib APIs with zero specification:

**Referenced but undefined:**
- `std/http` — Server, Response, Request, Middleware
- `std/db` — db, query methods
- `std/fs` — file operations
- `std/crypto` — crypto operations
- `std/process` — Context, environment
- `std/validate` — validation utilities
- `DateTime` — date/time handling
- `JSON` — JSON.parse, JSON.stringify
- `chan<T>()` — channel constructor
- `atomic()` or `Atomic<T>` — atomic types
- `Receiver<T>`, `Sender<T>` — channel types

**Impact:** Examples look complete but aren't implementable. No guidance on async vs sync, Result vs throw, API style.

**Fix:** Write **ADR-017: Standard Library Design** covering:
- Phase 1 modules (http, db, fs, process, crypto, validate)
- API conventions (async by default? Result vs throw?)
- Type design (branded types? newtypes?)
- Stdlib versioning (lock to language version? independent?)
- Defer to post-v1: full ORM, advanced networking, GUI

---

#### 7. MEDIUM: No FFI specification

**Issue:** `unsafe` blocks and `ffi.load()` are shown but not specified.

**Evidence:**
- `docs/language-reference.md:593` — shows `ffi.load("libcrypto.so")`
- No ADR on FFI

**Unspecified:**
- C type mapping (`int` → `int32_t`? `int64_t`?)
- Struct layout compatibility (repr, alignment)
- Ownership across FFI boundary (who frees what?)
- Callback support (can C call Coco functions?)
- String handling (UTF-8? null termination?)
- What `lib.fn("name")` returns (wrapper? raw pointer?)

**Impact:** Can't implement FFI without making arbitrary decisions.

**Fix:** Write **ADR-018: FFI Design**

---

#### 8. MEDIUM: No build system / package manifest design

**Issue:** `coco.toml` is mentioned only for safety settings. No spec for:
- Package metadata (name, version, authors)
- Dependency declaration
- Build targets (binary vs library)
- Compiler flags
- Test configuration
- Entry point specification

**Impact:** Can't build multi-file projects without inventing conventions.

**Fix:** Write **ADR-019: Build System and Package Manifest**

---

#### 9. MEDIUM: Magic methods `__get/__set` undermine type system

**Issue:** Once a class has `__get` or `__set`, the compiler can't know what properties exist.

```coco
class DynamicConfig {
    private data: map<string, mixed>;
    
    __get(key: string): mixed {
        return $.data[key];
    }
}

const cfg = new DynamicConfig();
print(cfg.apiKey);  // Does this compile?
```

**Unspecified:**
- Does `cfg.apiKey` type-check as `mixed`?
- Does the compiler warn on undeclared property access?
- Does this poison type checking for subclasses?

**Impact:** Type safety guarantees unclear.

**Fix:** Specify in **ADR-020: Type System Specifications** (see below)

---

#### 10. MEDIUM: No trait method conflict resolution

**Issue:** ADR-008 addresses property conflicts (compile error) but not method conflicts.

```coco
trait Timestamps {
    touch(): void { $.updatedAt = DateTime.now(); }
}

trait Auditable {
    touch(): void { $.touchedBy = getCurrentUser(); }
}

class Post {
    use Timestamps, Auditable;  // What happens?
}
```

**Impact:** Unclear whether this compiles or errors, and if allowed, which `touch()` is called.

**Fix:** Specify in **ADR-020: Type System Specifications** — recommend compile error unless explicitly resolved with `Timestamps::touch as updateTimestamp`

---

#### 11. MEDIUM: No match exhaustiveness specification

**Issue:** Docs show `match` with `_` wildcard but never state whether exhaustiveness is enforced.

```coco
fn handle(value: bool): string {
    return match value {
        true => "yes",
        // missing false branch — does this compile?
    };
}
```

**Unspecified:**
- Are enum matches exhaustive?
- Are bool matches exhaustive?
- Are union type matches exhaustive?

**Impact:** Error model examples imply exhaustiveness but it's not codified.

**Fix:** Specify in **ADR-020: Type System Specifications** — recommend exhaustiveness for enums and bool, optional for unions (with warning)

---

#### 12. MEDIUM: Object literal vs map literal confusion

**Issue:** Grammar calls `{ "key": value }` an `object_literal`, but type system docs show maps:

```coco
const config: map<string, string> = { "env": "production" };
```

Is this an object or a map? The distinction matters:
- **Objects** have nominal types, methods, and compile-time property checking
- **Maps** are structural, key-value stores with runtime lookups

**Unspecified:**
- Does literal syntax infer based on type annotation?
- Are map and object literals syntactically distinct?
- Can object literals have computed keys?

**Fix:** Specify in **ADR-020: Type System Specifications** — recommend:
- `{ key: value }` with identifier keys → object
- `{ "key": value }` or `{ [expr]: value }` → map
- Type annotation can coerce between them

### Category: Design Tensions (Acknowledge, Document, No Immediate Fix)

#### 13. ACKNOWLEDGED: "Full runtime magic" vs predictable latency

**Issue:** ADR-015 chooses automatic GC with no tuning knobs. The document acknowledges "latency is less predictable" and says "if a workload needs predictable latency, Coco may not be the right choice."

But the charter lists "high-performance APIs" as a target workload. High-performance APIs typically need predictable p99 latency.

**This is a genuine tradeoff, not a bug.** The design prioritizes developer ergonomics (no GC tuning) over tail latency guarantees.

**Recommendation:** Add a "Performance Expectations" or "Latency Characteristics" section to the charter or safety promise so users understand this tradeoff upfront.

---

#### 14. UNRESOLVED: The "colored function" problem

**Issue:** Async functions are eager (ADR-010). This creates a sync/async split with no bridge:

```coco
fn transform(data: string): string { return data.toUpperCase(); }

async fn main(): int {
    const data = await fetchData();
    transform(data);  // OK: sync called from async
    
    // But: can't make transform async-generic
    // Can't call async from sync without await
}
```

**Implications:**
- Higher-order functions like `map`, `filter`, `forEach` must be sync-only, async-only, or duplicated
- No way to write async-polymorphic code
- Rust solved this with `Future` trait, JS made everything async, Go uses goroutines

**Recommendation:** This needs an ADR before stdlib design. Options:
1. Accept duplication (`map` and `mapAsync`)
2. Make all stdlib async (forces everything async)
3. Introduce async trait abstraction (complex)

## Conclusion

The language design is **fundamentally good**. The issues are spec drift, not conceptual flaws. The grammar, docs, and examples need to be brought back into alignment.

**Priority order:**
1. Grammar fixes (critical blockers)
2. Module + stdlib ADRs (needed for implementation)
3. Type system specifications (needed for type checker)
4. Documentation cleanup

Once these are addressed, Phase 0-1 will be complete and Phase 2 (parser) can begin.
